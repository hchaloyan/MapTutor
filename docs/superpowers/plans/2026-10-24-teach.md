# Teach (Component 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The tutor teaches the approved graph node by node. `focus_node` moves the turn into a node's own thread. Quiz-checks drive node states, `set_node_state` adjusts them under guards, newly known nodes get a short summary, and node threads see the weak prerequisites, the approach, and the summaries in their study state. The study is done when the goal is known.

**Architecture:** `src/server/tutor/teach.ts` holds `focus_node`, `set_node_state`, `setNodeState` (shared with quiz-checks), and `summarizeNew`. A server tool can return `switchTo`, and `runTurn` then continues in that node's thread. The route runs `summarizeNew` after each turn through an injectable `summarize` seam.

**Tech Stack:** TypeScript, `node:sqlite`, `@anthropic-ai/sdk` (`messages.create` for the side call), Vitest.

**Spec:** [01-user-flow.md](../../../01-user-flow.md) (Teach), [02-agent.md](../../../02-agent.md) (server tools, summaries), [03-graph.md](../../../03-graph.md) (transitions, guards, prerequisite warning, next node)

## Global Constraints

- **Append-only history still holds.** A thread switch appends a `tool_result` in the old thread and a new user message (an `[App: …]` note plus the state block) in the node's thread. Nothing earlier is edited. A thread ending on a user message is fine, because the API merges consecutive user messages.
- **One turn per study.** The in-memory lock moves from per-thread to per-study, so a turn that switches threads can't race a second turn in its new thread.
- **Quiz-check transitions** follow `afterQuizCheck`. Items are grouped by `nodeId` within one quiz call; a node passes only if all its items in that call are correct. `ever_known` is set when a node reaches `known`, and the study moves to `done` when the goal does. `done` is not undone if the goal later slips.
- **`set_node_state`** uses `checkSetState`, where the checks are this node's check items grouped by `quiz_call_id` (`passed` = all correct, `at` = `answered_at`).
- **Summaries** are made for nodes with `ever_known = 1`, `summary IS NULL`, and some text in their thread, one Haiku call each, after the turn's `done` and the lock's release but before the response ends. A failure is logged and retried after the next turn.
- **Side call:** `SIDE_MODEL`, non-streaming `messages.create`, `max_tokens: 16000`, `output_config: { effort: 'low' }` (Haiku 5.5 defaults to `medium`), adaptive thinking left at its default.

## Rulings

- **Summaries run after the lock is released**, so the user can send the next message while they're written. Two turns ending close together on one study can both summarize the same node; `summary IS NULL` on the update keeps the first. Cost if wrong: one extra Haiku call.
- **A node known from the probe** is summarized after the first turn that leaves text in its thread, even if that lesson is partial. Summaries are never rewritten. Cost if wrong: a thin summary for that node.
- **App notes are hidden by their `[App:` prefix**, like state blocks by `<study_state>`. A user message that starts with `[App:` would also be hidden from the thread view.
- **`isAppText` lives in `context.ts`**, next to the code that writes state blocks, so both the thread view and the summary transcript use it.

## Review Focus

1. **A `focus_node` switch** leaves both threads valid for the next request: the old one ends with the `tool_result`, the new one with the note and state block, and every `tool_use` has its result.
2. **`focus_node` into a thread with a pending card** is an error, not a switch, so a `tool_use` is never followed by plain text.
3. **A known node failing a later check** goes to `frontier`, never `missed`; a quiz on two nodes moves each by its own items only.
4. **`set_node_state → known`** without a newer passed check is rejected.
5. **A summary failure** never breaks the response, and the next turn retries it.
6. **No answer leaks**: nothing in this component exposes quiz answers before they're given.

### Task 1: Thread switching and state transitions

**Files:**
- Create: `src/server/tutor/teach.ts`
- Modify: `src/server/core/db.ts` (`studies.focus_node_id`), `src/server/tutor/tools.ts` (`switchTo`, register tools), `src/server/tutor/loop.ts` (switch, `focus` event), `src/server/tutor/quiz.ts` (transitions), `src/server/tutor/context.ts` (state lines), `src/server/routes/studies.ts` (per-study lock, focus on node messages, `focusNodeId`, hide `[App:` notes), `prompts/app-appendix.md`, `04-data-model.md`
- Test: `src/server/tutor/teach.test.ts`

**Interfaces:**
- `ServerTool.run` may return `switchTo: string`. `Emit` gains `focus { nodeId }`.
- `focus_node({ nodeId })` (teach, done): sets `focus_node_id`. Same thread → `Already in node "x"'s thread.` Other thread → `Opened node "x"'s thread. The lesson continues there.` plus `switchTo`. Errors: `focus_node needs a nodeId.`, `Node "x" is not in this study.`, `Node "x"'s thread is waiting for the user to answer a card there. Keep teaching here, or ask the user to open that node.`
- Switch note: `[App: focus_node opened this thread. Continue the lesson for "<label>" here.]`
- `set_node_state({ nodeId, state, reason })` (teach, done). Error: `set_node_state needs a nodeId, a state (missed, frontier, or known), and a reason.`, the guard's message, or the unknown-node message. Success: `Node "x" is now frontier.`
- `setNodeState(db, studyId, nodeId, state)`: state, `ever_known`, `updated_at`, and `done` when the goal becomes known.
- Study state in teach and done: `Summaries of known nodes:` with `- id: summary` lines once any exist. In a node thread also: `This node: <description>`, `Weak prerequisites: a (missed), b (untested)` or `none`, and `Approach: …`.
- `GET /api/studies/:id` gains `focusNodeId`. Posting in a node thread sets the focus.
